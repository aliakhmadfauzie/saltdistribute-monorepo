# **SaltDistribute: Comprehensive PWA Specification & Technical Architecture(PWA) — Technical Specification & Blueprint**

## **1\. Project Overview & Architecture**

The platform is a mobile-first Progressive Web App (PWA) designed to manage wholesale and retail Item A distribution. It connects the business owner (Admin) directly with buyers via real-time stock visibility, role-based order management, manual payment verification, and automated push notifications.

### **Internationalization (i18n)**

The application must be designed to support two languages—English and Bahasa Indonesia—throughout the entire interface. This requirement encompasses all UI labels, push notifications, and dynamic content generated by the system. Implementation should utilize a lightweight i18n library, such as *react-i18next*, to manage translations efficiently while maintaining a small bundle size.

## **Zero-Cost Architecture Strategy**

The 100% free architecture will rely on your admin dashboard to silently manage order expirations and a client-side compressor to protect your storage limits.

### **Lazy Expiration System (Admin-Driven)**

* **Silent Background Query:** Every time you open the admin dashboard, a React hook automatically queries Firestore for any bookings with PENDING\_CONFIRMATION or AWAITING\_PAYMENT status where the createdAt timestamp is older than 24 hours. Additionally, an explicit REJECTED\_BY\_ADMIN status exists which immediately returns reserved Item A quantity to inventory.  
* **Batched Rollback:** If expired orders are found, your app executes a Firestore Batched Write. This securely loops through the expired orders, updates their status to CANCELLED\_UNPAID, and simultaneously adds the reserved Item A quantity back to your main inventory document.  
* **Zero-Cost Execution:** Because this routine runs on your device rather than a background Google server, it uses your daily free Firestore read/write quota instead of requiring a credit card for Cloud Functions.

### **Storage Optimization (Frontend Compression)**

* **Client-Side Processing:** Before a buyer's phone uploads a payment receipt to Firebase Storage, the React app uses a lightweight library (like browser-image-compression) to intercept the file.  
* **Aggressive Downsizing:** It instantly shrinks massive 5 MB smartphone photos down to approximately 200 KB while retaining enough clarity for you to verify transaction IDs and transfer amounts.  
* **Longevity:** At 200 KB per receipt, Firebase's free 5 GB storage limit will comfortably hold 25,000 active orders before you ever need to manually delete old files.

### **Concurrent Order Protection**

* **Device-Triggered Transactions:** The atomic transactions for locking inventory will run directly from the buyer's phone. When they click "Place Order," their device executes the read-and-write check. If someone else just bought the last gram of Item A, the buyer's phone aborts the write instantly, costing you zero backend processing power.

### **Security & Data Protection**

* **Public Read:** Only authenticated users can read the inventory collection.  
* **Owner-Only Write:** Buyers can only write to their own bookings collection where buyerId \== request.auth.uid.  
* **Admin Override:** Only users with role: 'admin' can write to the inventory collection or update booking.status. Admin roles are provisioned using a one-time local Admin SDK script or by checking the user's role field directly in the Firestore users collection.  
* **Immutable Order Properties:** Firestore Security Rules must explicitly forbid updates to price, discountAmount, or status if the request is not from an Admin, preventing client-side console manipulation.

### **Offline Support & Error Handling**

* **Offline Persistence:** Enable Firestore persistence so buyers can view past orders and stock status without an active internet connection.  
* **Retry Logic:** If a user clicks 'Place Order' while offline, the app queues the transaction locally and automatically syncs to the server once the connection is re-established.  
* Note: Placing an order requires an active internet connection for real-time atomic inventory validation; offline mode is limited to browsing catalog data and past orders.

> 1. **Access Provisioning:** Buyers can register directly via the sign-up form. Alternatively, the Admin can manually provision accounts for new buyers by creating a profile with a temporary password.  
> 2. **Order Submission:** The buyer checks stock availability on the top banner. If in stock, they select the gram package (100g, 500g, 1000g, etc.), choose self-pickup (COD) or warehouse dispatch, and click **Place Booking**.  
> 3. **Admin Order Acknowledgement:** The admin receives an immediate push notification. The admin opens the order dashboard, validates physical warehouse stock, and clicks **Accept Booking**.  
> 4. **Payment Submission:** The buyer receives a push notification instructing them to transfer the grand total. The buyer uploads a screenshot (JPG/PNG) or PDF invoice proof into the app.  
> 5. **Payment Verification:** The admin previews the uploaded receipt inside the admin panel. Once matched with the bank account balance, the admin clicks **Verify & Activate Order**.  
> 6. **Execution & Fulfillment:** The order moves to the **Confirmed / In-Delivery** queue with live status tracking visible to both parties.

## **6\. Real-time Notification Engine**

### **Trigger Matrix**

| Event Trigger | Recipient | Payload Title | Payload Body |
| :---- | :---- | :---- | :---- |
| Buyer submits new booking | Admin | New Item A Booking\! | \[Buyer Name\] placed an order for \[X\] grams. |
| Admin confirms availability | Buyer | Order Accepted | Stock confirmed\! Please proceed with payment. |
| Buyer uploads proof file | Admin | Payment Proof Received | Receipt attached for Order \#\[ID\]. Please verify. |
| Admin clicks 'Verify Payment' | Buyer | Payment Verified\! | Your booking is now valid and scheduled for dispatch. |
| Admin toggles stock switch to ON | All Buyers | Stock Alert | Item A inventory has been replenished. Book now\! |

### **Implementation Pattern & External Triggers**

> 1. **Service Worker (public/firebase-messaging-sw.js):** Intercepts background messages when the mobile browser/PWA is closed.  
> 2. **Foreground Handler:** Uses onMessage from @firebase/messaging to display in-app sliding toasts when the user is actively using the app.  
> 3. **iOS Support Provision:** Ensures proper display of the "Add to Home Screen" guide prompt, as iOS requires home screen installation to permit Web Push notifications.  
> 4. **Free Serverless Dispatch:** Use Cloudflare Workers or Vercel Serverless Functions (Free Tier) to listen to Firestore changes and dispatch FCM notifications, bypassing Google Cloud Functions costs.  
> 5. **WhatsApp Deep Linking:** Integrate 1-click WhatsApp buttons (wa.me) in the Admin and Buyer dashboards. Clicking the button opens WhatsApp with a pre-filled template (e.g., "Hi \[Admin\], I have uploaded payment for Order \#BK-123").

## **8\. Bookkeeping & Storage Management**

> * **Sales Data Export:** Admin dashboard includes a "Download Sales Report" feature that converts Firestore data into Excel/CSV locally using the xlsx library for offline bookkeeping.

**Storage Garbage Collector:** A dedicated Admin maintenance tool to batch-delete receipt images older than 180 days (6 months). This manual routine ensures the 5GB Firebase Storage limit is never exceeded while retaining essential historical records.

## **9\. Inventory Restock & Analytics**

### **9.1 Backend: Restock Logs & Aggregation**

> 1. **Restock Schema:** The restock\_logs collection contains documents with: quantityAdded (number), costPerTon (number), totalCost (number), and timestamp (serverTimestamp).  
> 2. **Aggregation Logic:** Metrics are aggregated client-side in the Admin dashboard by querying bookings (status: COMPLETED) for revenue and restock\_logs for COGS. Profit is calculated as Σ(grandTotal) \- Σ(totalCost).

### **9.2 Frontend: Restock & Analytics UI**

> 3. **Restock Modal:** A React component featuring a controlled form with validation. On submission, it triggers a Firestore writeBatch that adds the log entry and increments the inventory.currentStock field atomically.  
> 4. **Analytics Dashboard:** Uses Recharts or similar to visualize turnover. It employs a custom useAnalytics hook that memoizes calculations to prevent performance lag during data heavy exports to CSV.

## **10\. Real-time Buyer-Seller Chat**

> 1. **Backend Sub-collection:** Messages are stored in chats/{bookingId}/messages/{messageId}. Schema: senderId (string), text (string), timestamp (serverTimestamp), and isRead (boolean).  
> 2. **Security Rules:** Rules enforce allow read, write: if request.auth.token.role \== 'admin' || resource.data.participants.hasAny(\[request.auth.uid\]) to ensure private threads.

**Frontend ChatWindow:** Implemented using a React useEffect hook that initializes a Firebase onSnapshot listener on the message sub-collection. This provides real-time UI updates without manual refreshing.

### **5.3 Cross-Platform Chat System**

* **Chat Access Point:** A floating action button (FAB) or dedicated icon on every 'Active Booking' screen that launches the messaging modal.  
* **Message Thread Layout:** A clean, conversational UI showing real-time timestamps, sender identification (Buyer/Admin), and text input with an 'Enter' to send shortcut.  
* **Visual Indicator:** An unread message badge (numeric) on the chat icon when new messages arrive while the modal is closed.

**Persistence:** All message history is archived against the specific bookingId and remains accessible to the buyer for 30 days post-order completion.
